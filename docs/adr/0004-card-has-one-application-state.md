# 一張卡的投遞只存一個狀態,不再用十幾個可以任意組合的記號

以前一張卡從「可以投了」到「已投出」,是靠十幾個各自獨立的記號拼出來的(填過沒、頁在不在、送出過沒、確認過沒、履歷換過沒、送出結果不明……)。記號可以任意組合,幾萬種情況大多沒人想過;同一條規則又在看板、後台七八個地方各寫一次,各地方的條件不一樣,畫面講的跟程式做的就對不上(#297)。改成每張卡只存一個投遞狀態(還沒填、正在填或改、沒填成、停著等你、填了卡住、上傳的是舊檔、頁面不見了、你已確認、正在送出、送出結果不明、已送出),狀態之間怎麼走由一張「狀態 × 事件」表定義,每一格都填了;「停著的頁」「能不能確認送出」這類判斷先看狀態,再看一張固定的檢查清單(常用答案、投遞前驗收、客製版、確認時的答案快照),檢查清單不是狀態。

## Considered Options

- **記號照舊,用同一套規則和狀態組合表把它圍起來**:改動小、不動看板資料的存法,但只是治標:新增一個記號就要再想一遍它和其他記號的所有組合,漏一處就是 bug。
- **只存一個狀態(採用)**:要轉換既有看板資料,但錯的組合根本存不進去,邊角情況收斂成狀態表上看得見的格子。

## Consequences

- 看板資料的存法改變,舊資料在打開看板時轉成新格式;轉換要先在真實資料的副本上驗過。
- 「在可以投了、卻帶著已送出紀錄」這種卡不存在:agent 親手送出的卡不能退回,只能由使用者按「沒送成」,送出證據收進投遞歷史。
- 看板和後台各有一份讀狀態的判斷(看板要對還沒存的答案當場判斷),兩份用同一張狀態表逼成一致。
- 狀態只能透過事件改,連 agent 也一樣(#307):派出去的 agent 拿不到看板檔的位置,只拿到一個代號,它呼叫的小工具照代號找回那一份,而且只收狀態表允許的事件(例如記表單只在正在填或改時收)。看板檔每次正常寫入都記下指紋,讀檔時對不上就是被繞過改過,程式停下來回報、不照改過的內容做事,由使用者看過之後自己放行(`tools/board_doc.py --trust`)。
