# 網站任務:程式自己讀 agent 交回或開著的頁,前提破掉只准交給使用者

找缺、查應徵進度、幫你填表、平台履歷同步共用同一個核心:程式自己讀頁、照 ADR-0009 編號,agent 引段落編號,程式核對。找缺怎麼找是 agent 自己的事,程式不鋪路;agent 交回網址,程式用同一種讀法讀那個網址。查應徵進度、填表、同步要看的東西可能分在好幾頁、藏在要捲動或展開的地方(LinkedIn 的專案在另一頁),所以由 agent 把頁開好,程式讀 agent 開著的每一頁;會改動網站的任務(填表、同步)再比改前改後,每一處改動不論程式核對過沒有,都附改前改後的截圖列給使用者,用到這份平台履歷的卡送出前都要使用者看過最新一版;程式不分哪段是要改的、哪段是被誤刪的,也不另派 AI 分,只核對新的原文一字不差出現在改後新出現的段落裡,使用者按恢復的由 agent 恢復、程式再讀、再列一次。程式對網站押的每個前提都寫成測試,破掉時只准落到「附證據列給使用者看」或「明確停下說原因」,不准落到程式自己判通過或失敗;核對不過或讀不到的欄位,卡上把 agent 說的和程式讀到的原文並列、標成 agent 判斷,也不拿它自動篩卡或排序:程式自己找頁、自己判斷內容的意思,就要對網站做假設,而沒有一種做法對所有網站都成立(docs/research/2026-10-25-how-to-make-agents-generalize.md 第 7 節),ADR-0007 的例外規則就是這樣一條條長出來的。

## Consequences

- 不保證:平台上的檔換成同名的另一份、或只換了連結目標,頁面文字沒變時程式看不出來;改前改後都讀不到的內容(兩次都沒展開、在讀不到的節點裡)被改了;agent 沒開的頁(例如漏開專案那一頁)被改了,清單上會寫這次比了哪幾頁;沒動的項目被平台自己弄掉(只有只驗收會全部重驗)。本機是真相,下次同步會蓋回去。
- 使用者每次同步、填表改過平台後都要看完整份改動清單:分出「哪些不用看」要對網站做假設(字數上限、各平台自己的改寫),押錯就是誤刪沒人看到,再派一個 AI 分也還是要人兜底。
- 前提押錯的代價落在使用者要看的清單變長;實際把缺的履歷內容同步上去時,統計清單裡有幾筆其實沒事,用來判斷前提要不要改(改成對整類網站成立,不為單一網站加處理)。
